NIKA: your own link from gateway to platform

NIKA lets a Stargate send its data to ATLAS (or any NIKA platform) over an encrypted link, receive commands and writebacks back, and lean on a neighbouring Stargate when its own link is down. It runs alongside MQTT: nothing about MQTT changes.

Everyone

Three parts, one protocol

Each part is a separate package you can import. Specs live next to the code in the NIKA repo.

nika.secure

🔐 NSC: secure channel

Two parties prove who they are with public keys, then talk encrypted. It's built only from proven building blocks (X25519, ChaCha20-Poly1305, HKDF).

SECURE.md
nika.uplink

☁️ Uplink: gateway ⇄ platform

Data goes up and is acknowledged only once the platform has stored it. Commands come down. Relaying is announced, never hidden.

UPLINK.md
nika.mesh

🕸️ Mesh: neighbours help

Gateways on one LAN find each other and carry each other's traffic, separately for MQTT and NIKA, when a link fails.

MESH.md

Five ideas to remember

1
Alongside MQTT, not instead of it. A Stargate can send to MQTT, to NIKA, or to both at once. Turning NIKA on or off never touches MQTT.
2
Identity is a key pair. The public key is 43 characters of text. Its short form is an 8-character fingerprint such as 4f1c9a7e. Pairing = each side learns the other's public key.
3
An ack means stored. The gateway keeps each message in its outbox until the platform says it has written it. Rejections always come with a reason; nothing is dropped silently.
4
Relaying is explicit. When A carries B, the platform is told, decides whether to allow it, and stores the data under B. Commands for B travel back through A.
5
NIKA is only a protocol. It knows nothing about Stargate, ATLAS, BACnet or topics. Each application plugs in through callbacks.

    The mesh: neighbours that cover for each other

    When a Stargate loses its own link, it sends through a neighbour on the same LAN that still has one. This works per channel:

    MQTT channel

    The neighbour publishes B's messages on its own broker connection. The neighbour must use the same broker, and the broker's ACL must allow B's topics.

    NIKA channel

    The neighbour forwards B's data over its own NIKA uplink, marked as B's. ATLAS must know B and allow the neighbour to relay.

    Set it up

    Settings → NIKA → Mesh: enable it, enter the same mesh key on every gateway, then save. Neighbours appear within seconds. If broadcasts are blocked, add them as static peers (host:47800).

    NSC: the NIKA Secure Channel

    A Noise-IK-style handshake. The client already knows the server's static key, so the handshake is one round trip and authenticates both sides. Protocol name: NIKA-NSC-v1/IK/X25519/ChaChaPoly/SHA256. Click a token to see what it does.

    Message 1 · client → server (H1)

    Message 2 · server → client (H2)

    Click a token above.

    After the handshake

    PropertyHow
    Frameheader(12) = version ‖ epoch ‖ kind ‖ counter(8), then ChaCha20-Poly1305 with nonce = counter and AAD = header
    Replay / reorderCounters only move forward; anything else is rejected
    RekeyEach direction rolls its key every 220 frames or every hour
    Forward secrecyEphemeral keys on both sides; the client's identity is never sent in the clear
    KeysStaticKey.load_or_create(path) (file mode 0600), public_b64 (43 chars), fingerprint = first 8 hex characters of SHA-256(public key)

    Try it: fingerprint from a public key

    This is computed locally in your browser, the same way NIKA does it. Paste the two keys to check that a pairing matches.

    from nika.secure import StaticKey, ClientHandshake, ServerHandshake
server, client = StaticKey.generate(), StaticKey.generate()
hs_c = ClientHandshake(client, server.public)          # client knows the server key
hs_s = ServerHandshake(server)
client_static = hs_s.read_message1(hs_c.write_message1())   # server learns + authenticates the client
m2, s_sess = hs_s.write_message2()
c_sess, _ = hs_c.read_message2(m2)
assert s_sess.decrypt(c_sess.encrypt(b"hi"))[1] == b"hi"

    You rarely touch NSC directly: the uplink uses it for you.

    Uplink protocol

    ZeroMQ DEALER (gateway) ⇄ ROUTER (platform) over TCP, default port 47900. Frames: H1/H2 handshake, D NSC-encrypted JSON, and E plaintext refusal (only UPLINK_NOT_AUTHORISED). The maximum message size is 1 MiB. Pick a message:

    Guarantees

    ✓
    An ack means stored. publish() returns only after the server app's on_data returned. It raises UplinkError(reason) on a rejection and UplinkUnavailable when the outcome is unknown (retry; de-duplicate on msg_id).
    ✓
    Ordered and single. Messages from one peer are processed in order, and a new session for the same peer replaces the old one.
    ✓
    Commands are safe to repeat. They're de-duplicated by command_id and refused when past expires_at, before your handler runs.
    ✓
    Routes survive reconnects. They're replayed after a reconnect and dropped when the relay's session ends. Concurrent announce_route() calls for one origin share one request.

    Errors: UPLINK_NOT_AUTHORISED, UPLINK_ORIGIN_DENIED, UPLINK_STORE_FAILED, UPLINK_UNAVAILABLE, UPLINK_BAD_MESSAGE, or any reason string your on_data returns.

    Build a NIKA platform (ATLAS is the reference)

    A platform needs four things: a key, a server, an authorisation rule and a store.

    from nika.secure import StaticKey
from nika.uplink import NikaUplinkServer, DataMessage

key = load_or_create_platform_key()          # keep it safe: it IS the platform's identity

async def authorize(client_public: bytes) -> str | None:
    """A peer id (we use the key text) if this key belongs to a known, enabled gateway."""
    gw = await db.gateway_by_key(key_text(client_public))
    return key_text(client_public) if gw else None

async def on_data(dm: DataMessage) -> str | None:
    """Store, then return None (ack ok) or a reason string (explicit reject)."""
    gw = await db.gateway_by_key(dm.origin)  # dm.origin != dm.peer_id when relayed
    if gw is None:
        return "UPLINK_ORIGIN_DENIED"
    await store(gw, dm.topic, dm.payload)    # commit BEFORE returning
    return None

async def on_route(relay: str, origin: str, active: bool) -> bool:
    """May `relay` carry `origin`?"""
    r, o = await db.gateway_by_key(relay), await db.gateway_by_key(origin)
    return not active or bool(r and o and r.relay_allowed)

server = NikaUplinkServer(key, bind="tcp://0.0.0.0:47900", authorize=authorize, on_data=on_data,
                          on_route=on_route, on_session=on_session, on_command_ack=on_command_ack)
await server.start()

route = await server.send_command(peer_id, "stargate/gateway/sg-roof/cmd", payload_json,
                                  command_id=str(uuid4()), expires_at=time.time() + 120)
# 'direct' | relay peer_id | None (unreachable → mark the write "undeliverable")
    PieceATLAS (backend/atlas/services/nika_server.py)
    KeyCreated on first start and stored encrypted (Fernet, SECRET_KEY) in system_secrets, so it survives upgrades and backups. If it can't be decrypted, ATLAS refuses to replace it
    authorizeAn enabled gateway with transport='nika' and a matching nika_public_key
    on_dataIngestManager.ingest(gateway_id, topic, payload), the same single entry point MQTT uses. Topics ATLAS doesn't use are acked and ignored
    on_routeThe relay has nika_relay_allowed and the origin is a known NIKA gateway, so the UI shows “Connected via <relay>”
    EditsEditing or disabling a gateway calls server.disconnect(old_key)
    Writebacksservices/commands.py: builds Stargate's payload (point_id, data, priority, writebackId, command type) and sends it to <prefix>/cmd. The answer arrives as data on <prefix>/ack/cmd and is matched by writebackId. NOT_APPLIED supersedes SUCCESS; no answer in 60 s → timeout

    Build a NIKA gateway (Stargate is the reference)

    from nika.secure import StaticKey, parse_public_key
from nika.uplink import NikaUplinkClient, UplinkError, UplinkUnavailable

key = StaticKey.load_or_create("/data/nika/identity.key")
client = NikaUplinkClient(key, parse_public_key(PLATFORM_KEY), endpoint="tcp://atlas:47900",
                          meta={"base_topic": BASE, "gateway_id": GW}, on_command=handle_command)
await client.start()

# drain a durable outbox, oldest first
for row in outbox.unsent():
    try:
        await client.publish(row.topic, row.payload, msg_id=f"{GW}:nk:{row.id}")
        outbox.mark_sent(row.id)               # only after the platform stored it
    except UplinkUnavailable:
        break                                  # link dropped: try later, or via the mesh
    except UplinkError as e:
        outbox.mark_failed(row.id, e.reason)   # explicit rejection: don't retry forever

async def handle_command(cmd) -> str:
    if cmd.target:                             # for a neighbour we relay for
        return await mesh_forward(cmd)
    await run_locally(cmd.topic, cmd.payload)  # then publish the ack as normal data
    return "accepted"

    Security · everyone

    “Our own encryption”: what is NIKA's, and what isn't

    The goal was a custom, hard-to-break encryption model of our own. NIKA has one, and it is the NIKA Secure Channel (NSC). It has two layers, and only one of them is meant to be ours:

    NIKA's own protocolThe handshake shape, message layout, frame header, key schedule and labels (NIKA-NSC-v1…), rekey rule, replay rules, identity and fingerprint format, key-file format and error behaviour. Nobody else speaks NSC: a TLS, Noise or SSH client can't talk to a NIKA server.
    Standard, proven building blocksX25519 key agreement · ChaCha20-Poly1305 encryption + integrity · HKDF-SHA256 / SHA-256. These are the same blocks used by WireGuard, Signal, TLS 1.3 and SSH.

    Why not invent the cipher too?

    Security comes from secrecy of the design. But anyone with a Stargate image has the code, and the algorithm gets reverse-engineered. After that, only its real mathematical strength is left, and a cipher no expert has attacked usually has very little. This has happened again and again: the GSM ciphers A5/1 and A5/2, MIFARE Crypto-1, the DVD's CSS. All were secret, custom and broken, often with standard techniques (differential and linear cryptanalysis, nonce reuse, timing).
    Security comes from the keys alone (Kerckhoffs's principle). The design can be fully public and still nobody can read or forge traffic without the keys. The protocol is ours, so it stays unique to NIKA. The primitives are the ones the whole world has tried to break for years without success, so “hard to break” is a measured fact, not a hope.

    How hard is “hard to break”? Try it

    Pick an attacker. This is how long a brute-force search of NSC's 128-bit security level would take.

    PrimitiveSecurity levelBreaking it means
    X25519≈ 2128 operationsRecovering a private key from a public key
    ChaCha20-Poly1305256-bit key, 128-bit tagDecrypting is a 2256 search; a forged frame passes with probability ≈ 2−106 per attempt
    SHA-256 / HKDF128-bit collision, 256-bit pre-imageDeriving one session key from another
    What must stay secret: the keys, that is, each gateway's identity.key, and ATLAS's SECRET_KEY (which protects its NIKA key). The design itself doesn't have to be secret.
    Want a layer “known only to us” as well? Turn on the deployment-wide pre-shared key: a 32-byte secret mixed into the handshake (Noise IKpsk2 pattern, see NSC internals). Then even someone with a valid key pair and the source can't open a session. It's optional and off by default (psk= on NikaUplinkServer / NikaUplinkClient).

    Security · developer · interactive

    NSC internals: key schedule and frames

    State is a Noise-style chaining key ck and transcript hash h. Every public value and ciphertext is mixed into h and used as AEAD associated data, so changing any byte of the transcript breaks the next tag. Step through it:

      HKDF(ck, ikm) = HMAC-SHA256 extract with ck as the salt, then two expand blocks: out1 = HMAC(prk, 0x01) and out2 = HMAC(prk, out1 ‖ 0x02), exactly as in Noise. Message 1 is 0x01 ‖ e(32) ‖ enc_s(48) ‖ enc_payload(24+n); message 2 is 0x01 ‖ f(32) ‖ enc_payload(16+n).

      Optional pre-shared key (IKpsk2)

      With psk= on both sides (32 random bytes; generate_psk() makes one as text), the protocol name becomes NIKA-NSC-v1/IKpsk2/X25519/ChaChaPoly/SHA256, every ephemeral is also mixed into the key (ck, k = HKDF(ck, e)), and after se in message 2 the psk goes in: ck, h′, k = HKDF(ck, psk, 3), h = SHA256(h ‖ h′).

      Effect
      Version byte 0x02A psk peer and a plain peer fail on the very first byte with a clear NSCError, not on a puzzling tag error. The different protocol name means the two transcripts can never match
      Nobody without the psk can read message 2So they can't derive session keys, even with a stolen identity.key
      The server switches sessions only after the new session's first frame authenticatesA valid message 1 without the psk can't knock out the live session
      Message 1 is still readable without the pskA stranger's handshake costs the server the same two DH operations (gap 3 is unchanged)
      RolloutPlatform and gateways switch together: a psk server refuses all plain clients, and a plain server refuses all psk clients

      What the uplink server and the mesh enforce

      Uplink server

      • authorize(key) on every connect, after proof of key ownership
      • one session per identity, switched only once the new session's first frame authenticates; ATLAS edit/disable → disconnect()
      • optional deployment pre-shared key (psk=)
      • relayed data needs an accepted UPLINK_ROUTE
      • 1 MiB per message, 10,000-message queue per session, 30 s idle timeout
      • the platform key is stored Fernet-encrypted (ATLAS)

      Mesh

      • HMAC-SHA256 on every frame, compared in constant time
      • ±120 s timestamp + unique frame id (replay cache)
      • ZeroMQ identity must equal sender; optional allowed_peers
      • 200 msg/s per origin, relay_capacity, 10 s idle drop
      • origin identity: RELAY_CHALLENGE {n, e} → RELAY_PROVE {mac}, mac = HMAC(HKDF(DH(S, E)), relay ‖ origin ‖ n ‖ E ‖ S ‖ meta); the relay exposes the proven key as session_identity()
      • NIKA channel: same-platform check, origin named only by its proven key, then the platform's route decision

      Commands

      • unique command_id + expires_at
      • duplicates and expired commands refused before the app sees them
      • one CommandGuard shared by the uplink and the mesh: a command runs at most once
      • the device's answer is tracked separately (writeback states)

      Wire formats, messages and error codes

      Uplink (ZeroMQ DEALER ⇄ ROUTER)

      [kind, data] from the DEALER (the ROUTER adds the identity). Kinds: H1, H2, D (an NSC frame holding compact JSON {"t": TYPE, …}), E (plaintext {"code": "UPLINK_NOT_AUTHORISED"}). Payloads go in p (UTF-8) or pb (base64). MAX_FRAME = 1 MiB, enforced with zmq.MAXMSGSIZE.

      Writing an NSC peer in another language

      1. Implement X25519, ChaCha20-Poly1305 (IETF, 96-bit nonce) and HMAC-SHA256.
      2. Follow the key schedule above byte for byte: init with the protocol name, mix S_pub first, tokens e, es, s, ss / e, ee, se, a big-endian u64 timestamp as the first 8 payload bytes of message 1, and split → (c2s, s2c).
      3. Frames: a 12-byte header (>BBHQ) as AD; the nonce is 4 zero bytes ‖ the counter as LE u64; rekey label NIKA-NSC-v1 rekey.
      4. Test against Python: run your client against NikaUplinkServer and check that sessions() shows your fingerprint.

      Vendoring and versioning

      Copy nika/secure, nika/uplink, nika/mesh, nika/protocol.py and nika/envelope.py into the app (Stargate gateway/NIKA/, ATLAS backend/atlas/vendor/nika/). Never edit the copy: change NIKA, run its tests, re-copy. Byte 0 of every handshake message and frame is the NSC version. An incompatible change becomes NIKA-NSC-v2 with a new version byte, so old and new peers fail cleanly.
